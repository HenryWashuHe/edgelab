# EdgeLab: reliability reference and debugging experiment

## Current scope decision

A read-only [independent application assessment](PRODUCT_VALUE.md#independent-application-assessment-stale-subscriptions) found a reported Cloudflare OS delivery failure and an existing proposed fix. Ordinary reads and replay already establish persistence; callback fulfillment does not establish client application. Defer a server-only stall diagnostic. Any further experiment must compare independently sampled server positions with the real client's successful application boundary and add an answer beyond existing recovery and telemetry. The incident has not been reproduced by EdgeLab, and external demand remains unproven.

The [standalone counter inspector](evidence/counter-inspector/README.md) now supports recipient inspection from one copied file and Node, without a repository or npm install. Nine actual distribution test groups cover both pinned profiles, strict input bounds, renamed/symlinked execution, unwritten FIFO rejection and unchanged fixture files. This removes a distribution prerequisite; capture remains app-specific, and useful external adoption and faster diagnosis remain unproven. The production application and deployment are unchanged.

The [October 1 product value assessment](PRODUCT_VALUE.md) finds demonstrated portfolio/reference-application value but no validated unmet monitoring need. Further scope should test one independent Durable Object debugging workflow: explain what committed after a timeout, reset or lost response using bounded shareable evidence. Existing monitoring, SLO and Cloudflare replay tools already overlap substantially. Maintain the deployed service and address demonstrated correctness failures; defer generic feature expansion until portability and useful external use are established. The release and acceptance history below records shipped engineering, not market demand.

Acceptance requirements (completion requires evidence for every item):

- A real scheduled Worker checks deployment-approved HTTPS services and private service bindings without an open browser. Public callers cannot choose targets or trigger probes.
- SQLite-backed monitoring persists checks, service policies, incidents, acknowledgement, and audit events across eviction and deployment. Existing laboratory data remains compatible.
- Duplicate/retried/overlapping schedules cannot double-count samples or create duplicate incidents. Leases recover interrupted work; stale completions cannot overwrite changed policies.
- Incidents open after consecutive bad observations, recover after consecutive good observations, and permit authenticated acknowledgement with a bounded operator note.
- Reporting includes observed good-check ratio, latency percentiles, error-budget consumption, missing-sample coverage, freshness, and explicit measurement limits. Gaps never become successful checks.
- Scheduled checks start only in the current UTC minute. Delayed invocations are skipped with persisted diagnostic evidence and never backfill history. Each new check retains its actual start timestamp; a completion crossing a minute boundary keeps the original slot. Migrated checks with unknown start time remain visible but receive no verified SLO credit.
- `GET /api/ready` evaluates persisted scheduler completion and active-service freshness against an inclusive three-minute bound. Only healthy readiness returns 200; starting, partial, and stalled return 503. Paused services are ignored, and dashboard reads cannot renew the evidence.
- Fixed rule version 1 evaluates sampled-check burn over paired 60/5-minute windows at 14.4×, 360/30 at 6×, and 4,320/360 at 1×, based on the Google SRE 30-day budget examples. Both windows must meet the threshold. Signals remain separate from consecutive-failure incident transitions and external notifications.
- Each signal window exposes its exact finished-minute range, full expected minutes, verified good/bad observations, maintenance, unknown slots, coverage, burn, and current-policy maturity. Missing, legacy, wrong-revision, incorrectly timed, and conflicting duplicate observations cannot improve evidence; exact duplicates count once.
- Explicit project gates require full current-policy windows, at least 95% verified coverage in each, at least 20 non-maintenance observations in the long window, and five in the short window. Current pause or fully verified all-maintenance pairs show maintenance; mixed maintenance cannot bypass sample gates.
- A qualified firing rule takes priority over insufficient longer-window history; highest priority is rapid, then sustained, then gradual. A partially qualified rule set never conceals firing or becomes a confident all-clear result. The one-minute sampling granularity and the 99.9% target's coarse single-failure signal are documented without claiming customer-request availability.
- The coordinator computes and persists signals after scheduled probes complete. Public reads and exports expose the latest evaluation without reevaluating it. Same-revision evidence is current through an inclusive 180,000-millisecond bound; stale, changed-policy, and not-evaluated states cannot imply clearance.
- One last firing record per configured service survives insufficient evidence, maintenance, policy changes, stale scheduling, and later clear results. The UI distinguishes historical warning evidence from current firing and same-policy qualified clearance. Signals do not resolve incidents or send notifications.
- Warning evidence captures a self-contained, public-safe policy version with original service name, good-check target, latency/timeout, contract, transport, recorded time, and provenance. It survives pruning of 30-day checks and unreferenced source versions. Older warnings explicitly report unavailable context; reads never fill the gap from mutable current settings. New confirmation can capture a matching version without asserting that a legacy warning had context at its initial firing.
- The browser continues aging displayed budget evidence when status refreshes fail, without asserting that the server's scheduler stopped. A confirmed operator write remains confirmed if its follow-up status/audit read fails. Uncertain note submissions keep their request ID and exact body in authenticated Operations memory across investigation close/reopen; Lock, credential changes, leaving Operations, and reload clear that private session state.
- Public incident lists include every open incident for active deployment targets plus their latest 100 resolved incidents. `GET /api/ops/incidents/<id>?before=<slot>` provides 50 descending retained checks per page, lifecycle timestamps, retention bounds, and policy versions referenced on the page. Older open incidents cannot be hidden by a recent resolved-record limit.
- Policy versions captured at enrollment and subsequent changes preserve their context with `recorded` provenance. Migration labels the available current policy `recovered-current` and does not invent older policy history. Missing historical versions remain unknown.
- A valid bearer token adds private evidence to incident detail. `POST /api/ops/incident-note` supports a UUID v4 request ID, a 1–500-character nonblank note, at most 100 retained notes per incident, and idempotent retries of an identical payload. Conflicting reuse returns 409; recovered incidents permit follow-up notes.
- Public operations UI includes service health, history, incidents, reliability trends, export, and methodology; owner controls support policy editing, maintenance pause, and acknowledgement. The laboratory remains available.
