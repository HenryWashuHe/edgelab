# Reproduce incident-brief preparation offline

The evaluation harness uses three hand-authored, clearly labeled controlled scenarios. They are never inserted into the monitor and are not observations from a production incident. The harness requires installed project dependencies and Node 22.12 or newer. It does not use Cloudflare credentials, query an account, start Wrangler, call a model, or write production data.

```sh
node scripts/brief-evaluate.mjs
node scripts/brief-evaluate.mjs --verify
```

The first command asserts the controlled expectations and saves `output/brief-evaluation-offline.json`. The second recomputes the evaluation and compares it with the saved report without replacing it. Any changed evidence, prompt, model, project version, environment, or validation outcome fails comparison; regenerate the artifact intentionally after a change. `output/` is ignored by Git. Running `--help` describes these commands; unsupported arguments, including `--live`, fail before evaluation. There is no implemented native execution mode.

The harness bundles the actual `captureBriefEvidence`, `hashBriefEvidence`, `buildBriefInput`, `runIncidentBriefAI`, `decodeBriefResponse`, and `validateBriefOutput` exports. A controlled fake binding returns human-authored native envelopes. It verifies the server-selected model, abort signal, busy rejection, non-streaming request, temperature zero, and output token cap. Fetch is disabled. Each eligible fixture gets exactly one fake dispatch with no retry; insufficient evidence gets none.

| Controlled scenario              | Hand-counted evidence                                                                                                                    | Expected disposition                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| HTTP errors and sampled recovery | Eight finished minutes; three HTTP 503 checks and five good checks, including two later good samples                                     | Accept the canned HTTP hypothesis with a relevant supplied citation                                |
| Timeout and mixed gaps           | Seven checks across eight finished minutes; two timeouts, one slow, two good, one maintenance, one legacy HTTP error, one missing minute | Accept canned latency and evidence-gap hypotheses; finished-slice coverage is 5/7 eligible minutes |
| Insufficient history             | One verified good, one maintenance, one legacy HTTP error and one invalid-start timeout                                                  | Skip prompt preparation and dispatch because there is no verified bad observation                  |

Capture uses a fixed UTC time from the fixture module. The report contains the immutable public evidence snapshot, canonical SHA-256 evidence hash, prompt and schema versions, exact prepared input and its hash, actual UTF-8 message/input/envelope byte counts, included citation IDs, and explicit omitted-reference count. The full selected snapshot and the smaller representative model context are separate. Private sentinel notes and acknowledgement text must be absent from both. Stable replay and hand-counted facts are assertions, including maintenance exclusion and unknown legacy timing.

Adversarial checks require rejection of invented citations, citations for an unrelated symptom, unexpected root fields, HTML, and provider tool calls. When the prompt omits a retained reference, the harness also verifies that a model cannot cite that unsupplied entry. These checks invoke the production decoder and validator directly and do not dispatch even a fake request.

Acceptance establishes schema validity and relevance to recorded symptoms. The canned explanations remain unverified hypotheses. The input snapshots supply lifecycle events rather than exercise the incident transition reducer or scheduler. This suite measures neither model accuracy nor native provider behavior, token usage, cost, latency, or production incident outcomes. Its report explicitly records zero native calls, account queries and production writes. Do not present canned acceptance as an AI benchmark or a proven root cause.

## Public controlled explorer

Open [Fieldnotes](https://edgelab-reliability.edgelab-henrywashuhe.workers.dev/#notes) to inspect the three controlled cases without an operator token. Explanations are explicitly human-authored canned responses, with zero native inference. The insufficient case has no prepared input or response. Citations, historical UTC capture time, policy versions, fixture lifecycle, omissions and snapshot/input hashes remain inspectable. Local verification uses the same canonical snapshot-hash function; an altered clone demonstrates content sensitivity without changing the frozen source. A hash match cannot establish authenticity, recovery or root cause.

`scripts/brief-examples.mjs` generates `src/brief-examples-data.json` from the fixed archived 3.3.2 evaluation report. Only whitelisted public presentation fields enter the client bundle; raw prompts, provider envelopes, harness environment and private request fields are excluded. Run `npm run test:examples` to check exact projection equality; explicit `node scripts/brief-examples.mjs --write` regenerates it. Unit tests also compare these snapshots and hashes with current production capture/preparation/validation exports. The source artifact and reproduction guide links pin commit `67b27d01aacefdae1d6b5918240d54b9ddeb4769`.

Scenario selection, citation disclosure, hash verification and altered-copy comparison make no application API requests. Direct `/#notes` asset loading does not mount the live Operations or lab data flow. This makes a controlled demonstration inspectable during a storage outage; it does not supply new production monitoring or model-execution evidence.

## A future bounded native demonstration

Native execution is a separate, currently unimplemented step. Reuse the controlled fixture module and production exports in an isolated temporary Worker with a Workers AI binding managed by Wrangler. Keep its fixture endpoint on loopback, separate from the deployed monitor and its Durable Objects. Use supported Wrangler authentication; never read or extract OAuth secrets into an ad hoc REST client. Ordinary startup, health checks and GET requests must not infer. An explicit manual action should select a known fixture ID and reserve its single dispatch before calling the binding. Cloudflare documents that an AI binding accesses the account and consumes usage even during local Wrangler development. [Workers AI bindings](https://developers.cloudflare.com/workers-ai/get-started/workers-wrangler/)

Before enabling that path, verify the current account plan, model entitlement and account usage with the operator. Require a Free account with no paid-plan change for this project's demonstration. Local application limits cannot reserve the shared account allocation. Cloudflare currently grants 10,000 neurons per day across the account; Free requests fail beyond the allocation, while paid excess can incur charges. Other applications may have consumed the allowance. [Workers AI pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)

Bound a future run to these three known cases, at most two native calls total, one per eligible fixture, and no automatic retry or schema repair. Persist a local run ledger with reserved fixture IDs before dispatch so a connector restart or unknown response cannot silently repeat inference. Keep the insufficient case as a zero-call assertion. Preserve the current 2 KiB message cap, 4 KiB serialized input cap, 512 output token cap, 8 KiB envelope cap and 20-second abort deadline. Bytes are not a token count or a guarantee of remaining quota. The selected model is `@cf/meta/llama-3.3-70b-instruct-fp8-fast`; verify its current availability before any demonstration. [Model reference](https://developers.cloudflare.com/workers-ai/models/llama-3.3-70b-instruct-fp8-fast/)

Write a separately labeled native report containing the exact snapshot/input hashes, actual response validation, any reported provider usage, sanitized failures and unverified hypotheses. Preserve invalid output as a failed result. Never fabricate a production incident to make the demo work, turn provider failures into successful canned results, or imply that temperature zero makes native outputs reproducible.

A truthful resume description is: “Built a reproducible evaluation harness for Cloudflare Workers AI incident briefs, with immutable evidence hashes, bounded prompts, strict citation validation, and controlled failure and coverage-gap scenarios.” Native execution and model-quality claims require separate measured evidence.
